# Maintain the tooling

## When to use

- Upgrading packages or the toolkit itself.
- Installing or removing Git hooks.
- Running an Anarchy target that has no make target.
- Adding make targets, or keeping the agent skills in step with them.

## Workflows

**Update dependencies**: `make upgrade_dependencies INSTALL_TOOL=true` lists outdated packages; with the user's
agreement, add `UPGRADE=true`. Respect the compatibility notes in `Directory.Packages.props`, then run
`make compile test_unit`. Without the flags it prompts, which fails in non-interactive shells.

**Git hooks**: `make git_hooks_enable OPTIONS="--dry-run"` previews the pre-commit hook (lint fix and tests); run it
without `--dry-run` once the user agrees. `--force` replaces an existing hook: ask first.

**Build targets**: every operation has a make target; for anything else, `make anarchy_help` lists the build targets
and parameters, and `make anarchy TARGET="<Target> --<Parameter> <value>"` runs one. `make fallout`, `make nuke` and
their `_help` variants remain compatibility aliases.

**Boilerplate**: `make boilerplate ITEMS=Makefile,scripts APPEND=true` installs packaged files into the solution. It
never overwrites: on a conflict it writes nothing and lists the files. Look before writing:

- `make boilerplate_diff ITEMS=Makefile,scripts` (or `anarchy-toolkit boilerplate diff Makefile scripts`) prints a
  unified diff from the solution's copies to the packaged ones; `anarchy-toolkit boilerplate list` and
  `boilerplate show <path>` read the packaged files without installing anything.
- `make boilerplate ... DRY_RUN=true` reports what an install would create, keep, update or refuse.
- `.gitignore` and `.editorconfig` hold the toolkit's settings in a managed block (`# >>> anarchy-toolkit` ...
  `# <<< anarchy-toolkit`): never edit inside it; put the solution's own entries below it (in `.editorconfig`, repeat the
  section, such as `[*.cs]`, and set the override there: later entries win). `APPEND=true` replaces
  only that block, and warns about tracked files the new `.gitignore` ignores: ask the user whether to untrack them
  or add a `!` exception.

To pick up a newer Makefile or scripts, diff them and propose the changes to the user.

**Agent skills**: skills live in `.agents/skills/<name>/SKILL.md`. A `#@ <skill>` comment ties make targets to a skill:
at the top of a `.mk` file for all its documented (`#?`) targets, or right below one target for just that one (`#@ -`
exempts it; a bare `#@` means `<solution-prefix>-<file>`).
1. When adding a make target, document it with `#?` (and `#+ VAR|type|description` for its variables) and mark it.
2. `make skills_sync` creates missing skills from a template and rewrites only the block between the
   `anarchy:commands` markers. Everything else in a skill is free text: replace the template's TODOs with when to use
   the commands and how to combine them, as this skill does.
3. `make skills_validate` (run in CI) fails on missing skills, placeholder descriptions, missing `## When to use` or
   `## Commands` sections, or outdated commands.

`make install_skills` (or `anarchy-toolkit skills install`) installs the toolkit's skills; existing files are kept.

**Write a skill for your own Make targets**: add `#?` descriptions (and `#+ NAME|type|description` for parameters) to
each documented target. Put `#@ <skill-name>` at the top of a `.mk` file to assign all its documented targets, or
immediately below one target to assign just that target; use `#@ -` to exclude it. Then run `make skills_sync`, replace
the generated skill's TODO text with the workflow and cautions, and run `make skills_validate`.
