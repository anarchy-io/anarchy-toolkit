# Versions, packages and images

## When to use

- A package's code changed and needs a new version and release note.
- Checking that a branch's version bumps are complete, as the pull request check does.
- Packing, publishing, or building and pushing a container image, when the user asks.

## Workflows

**Bump a changed package**: `make release_bump RELEASE_PROJECT=<Project> RELEASE_BUMP=patch|minor|major` (patch for
fixes, minor for features, major for breaking changes). It also bumps every package depending on it.
- Never edit `<Version>` by hand.
- Bump from the base branch's versions and run it once per change: each run bumps again.
- A package never published keeps its initial version (e.g. `1.0.0`) even if bumped as a dependent; revert that bump.
- Several packages changed: `make release_bump_changed RELEASE_BASE=main` bumps all of them.

**Release notes**: commit the changes first, then `make release_notes RELEASE_BASE=main` adds a `### <version>` entry
under `## Releases` in each changed package's `RELEASE-NOTES.md` from the commit titles. Review the notes.

**Check**: `make validate_release RELEASE_BASE=main` fails when a changed package or one of its dependents lacks the
bump it needs. Run it before committing versions.

**Pack and publish**: `make list_packages` and `make pack` (into `artifacts/packages`) are safe. `make publish` pushes to
a feed and cannot be undone: only run it when the user asks, with the feed URL they give, and never print or commit API
keys.

**Container images** (builds implementing `IContainerBuild`): `make container_publish_app_artifact`,
`container_image_build`, then `container_image_push`, each with `APP_NAME=<project>`. Pushing changes a shared
registry: confirm with the user first.
