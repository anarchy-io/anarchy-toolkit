# Local environment and mock server

## When to use

- Integration or end-to-end tests, or a running application, need a database, broker or other local service.
- An external HTTP API must be mocked, or its mock expectations refreshed from an OpenAPI specification.

## Workflows

**Docker environment** (`docker/docker-compose.yml` by default): `make start` brings it up; pass
`WAIT_FOR="db broker" HEALTHY=true` to block until those containers are healthy before running tests. Use
`make container_logs CONTAINER=<name>` when something fails against a container, and `make stop` when done.
- `make destroy` deletes the volumes and their data; `make docker_stopall` stops every container on the host,
  including other projects'. Ask the user before either.
- When `make start` fails, check `make docker_info` first: Docker may not be running.

**Automatic test preparation**: opt in with `ITestEnvironmentBuild` on the Fallout build class and configure
`docker.waitFor` and `docker.waitForHealthy` in `.anarchy-toolkit.json`. Integration and end-to-end targets start
and wait for Compose; unit tests do not. `make prepare_test_environment` runs the preparation without tests.
Containers and their volumes remain in place after testing.

**Owned database migrations**: add `IFlywayBuild` to expose `make flyway_migrate` and `make flyway_info`, configured
with `FLYWAY_CONFIG_FILES`, `FLYWAY_LOCATIONS` and, for Compose services, `FLYWAY_NETWORK`. When combined with
`ITestEnvironmentBuild`, migration runs after Compose readiness and before tests. `make flyway_info` never starts
Compose. See the [Automation.Build package guide](https://anarchy-io.github.io/anarchy-toolkit/packages/Automation.Build/).

**Mock server** (a runnable project ending in `MockServer`): prefer `make mock_server_start` (background, waits until
ready, logs in `artifacts/mock-server/mock-server.log`) over `make mock_server`, which blocks until Ctrl+C. Stop it with
`make mock_server_stop`. `make test_integration_mocked` and `make test_end_to_end_mocked` start and stop it around the
tests and expose it as `MOCKSERVER_URL`. Recorded requests go to `artifacts/mock-server/requests.jsonl`.

Before concluding the mock server lacks something, check what it already does (guide:
https://anarchy-io.github.io/anarchy-toolkit/guides/mock-server.html, and the `Anarchy.Toolkit.Web.MockServer` and
`Anarchy.Toolkit.Testing.MockServer` package READMEs in the NuGet cache):

| Need | Use |
|---|---|
| Fixed answers | Expectation files in MockServer's JSON shape |
| Computed answers, fake auth, proxying | A middleware in the host's `Program.cs`: `MockServerEntryPoint.RunAsync(args, server => server.Use(...))`; `context.GetMockServer().Expectation` is `null` when nothing matched |
| One answer for one test | `MockServerClient.AddExpectationAsync`, then `ResetAsync` |
| What the application sent | `AssertReceivedAsync` / `ShouldHaveReceived`, or `RecordedRequestsFile.Read(...)` after the run |
| Fail on unmocked calls | `RecordedRequestsFile.Read(...).ShouldAllHaveBeenMatched()` |
| Record a real upstream as expectations | The guide's recording middleware (forward unmatched requests, save each answer as a file); review before committing |

**Setting it up**: a runnable project ending in `MockServer` with `MockServerEntryPoint.RunAsync(args)`,
`IMockServerBuild` with `MockServerExpectations`, a pinned `MockServerPort`, `ResetAsync` between tests,
`AssertReceivedAsync` for what was sent and `ShouldAllHaveBeenMatched` for unmocked calls. Callbacks, templates and
proxy forwarding are not built in: use a middleware, such as the recording one.

**OpenAPI changes**: `make mock_server_sync_openapi SPEC=<file-or-url> DRY_RUN=true` first and show the user what
would be added; then run it without `DRY_RUN`. It only adds expectations for new endpoints and reports changed or
removed ones: update those by hand, and review and commit the new files.
